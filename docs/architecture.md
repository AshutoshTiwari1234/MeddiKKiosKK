# MediKiosk architecture (Phases 1–6)

The browser app is a JavaScript SPA with independent staff and patient routes. React Router owns navigation, Redux Toolkit holds small shared UI state, and Axios provides the API client boundary. Presentational layout is split into reusable components so role-specific navigation and screens can grow independently.

The Node.js service exposes a versioned `/api` surface. Express middleware applies security headers, a narrowly configured CORS policy, bounded JSON parsing, and request logging that omits query strings and redacts patient/user record IDs. A centralized JSON error handler keeps unexpected errors from leaking details. `/api/health` reports MongoDB readiness and returns `503` while the database is disconnected.

Phase 2 adds MongoDB-backed staff identity and patient schema foundations. Staff sessions use short-lived HTTP-only JWT cookies; every protected request reloads the active user and role from MongoDB, and role checks are enforced in the API. Public account requests are limited to doctors and receptionists and remain inactive until an administrator approves them; administrator accounts are provisioned separately. Administrators can approve or reject requests and deactivate/reactivate accounts. Password changes increment a session version and invalidate prior tokens. Login attempts and account requests are rate-limited, and accounts temporarily lock after repeated failed logins. Audit events capture authentication and account changes without copying clinical data.

Phase 3 exposes public kiosk registration only after explicit case-taking consent. Registration issues a cryptographically random, two-hour intake token; MongoDB stores only its SHA-256 hash, and successful completion revokes it. Public endpoints accept only allowlisted registration/history fields with Zod validation and rate limits. Patient search and detail endpoints require staff authentication and are audited. Receptionists receive a reduced view without case history or ABHA ID; doctors and administrators can view the full patient-reported history. No AI output or diagnostic recommendation is generated in this phase.

Phase 4 adds clinician-controlled review and Ayurveda documentation. Patient-reported `caseHistory` remains unchanged; verified history and doctor notes live in a separate review object. Review status transitions and revisions are audited, with prior clinician review snapshots preserved. The structured Ayurveda assessment records Dashavidha Pariksha and related fields, along with assessor and timestamp. Only doctors and administrators can read or edit these clinical sections; the receptionist response projection removes them.

Phase 5 adds a Python/FastAPI conversation endpoint behind an Express proxy. The proxy verifies the short-lived intake capability, checks the patient's AI-assistance consent, validates the requested history field, and forwards only that answer and language. No patient identity is sent to the AI service. The default service runs a deterministic demo engine; an optional OpenAI-compatible adapter is disabled unless explicitly configured with server-side credentials. Neither mode may diagnose or recommend treatment. A timeout or service error falls back to the existing guided flow. The kiosk uses browser speech recognition and synthesis only after the patient activates those controls; browser-specific speech processing applies.

Phase 6 adds private document storage and a separate medical-document collection. Upload authorization verifies the patient intake token and document-processing consent before Multer writes a file. MIME type is checked against file signatures, size/page limits apply, filenames are random, and files are not served as static assets. The AI service extracts embedded PDF text and uses Tesseract for scanned pages and images. OCR results and candidate values remain unverified. Doctors and administrators alone can download originals, correct extracted text, and mark a document reviewed; each sensitive operation is audited.

Clinical history summaries are assembled from case history, clinician-verified values, Ayurveda assessment, and clinician-reviewed document text. They are saved as drafts and require an authorized clinician to approve. If AI-assistance consent is present, the backend may send de-identified structured source fields to the configured provider through the AI service; without consent, summary assembly stays in the backend. Provider-generated text remains a draft and is versioned when edited or regenerated.

The Python/FastAPI AI service sits behind the backend boundary. The backend performs a limited local urgent-phrase check before any AI forwarding, including when AI assistance is disabled. A matching response creates a patient-linked alert without retaining the answer text; staff acknowledge and resolve alerts from the dashboard. The check is not a diagnosis or complete triage system, and the kiosk continues to tell patients to alert staff directly.

Consent changes during intake are timestamped snapshots. Turning off AI or document processing takes effect on the next request; withdrawing case-taking consent revokes the intake capability. Doctors and administrators can download an audit-logged FHIR R4 collection Bundle after a clinician approves the summary. The bundle contains a Patient and DocumentReference resource and is not transmitted to a remote server. ABDM sandbox authentication, profiles, consent-manager flows, and network exchange remain deployment integration work requiring a registered sandbox client.
